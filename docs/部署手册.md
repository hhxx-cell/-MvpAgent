# MVP 部署手册

## 适用范围

本手册面向**合成数据演示环境**。当前项目的认证使用固定演示令牌；接入真实用户、真实订单或公网访问前，必须替换认证适配器并完成安全与容量评估。2026-09-29 已在 Linux 服务器实测以下 Compose 启动与端到端请求，证据保存在 [`evidence/compose-server/`](evidence/compose-server/summary.json)。

## 前置条件

- Docker Engine 与 Docker Compose 插件。
- 可拉取 Python 基础镜像和 `qdrant/qdrant:v1.13.6` 的网络，以及安装锁定 Python 依赖的网络；构建完成后默认规则网关不需要公网模型。
- 预留足够内存和磁盘空间保存镜像、Qdrant 索引及运行时状态。本次在总内存约 1.7 GiB 的服务器上完成演示冒烟，三个容器的 `docker stats` 单次采样合计约 251 MiB；该快照不能推导并发容量或生产 SLO，实际资源预算需压测确定。
- 仓库中保留 `pyproject.toml`、`uv.lock`、`database/schema.sql`、`database/schema_catalog.yaml` 和生成脚本。

## 启动与验证

从仓库根目录执行：

```sh
docker compose -f docker/docker-compose.yml up --build -d
docker compose -f docker/docker-compose.yml ps
docker compose -f docker/docker-compose.yml logs --tail=100 api
```

Dockerfile 使用 `uv.lock` 安装依赖，在镜像构建阶段执行固定种子生成与清单校验。Compose 启动 `qdrant`、`mock`、`api`；API 启动时把知识文档写入 Qdrant。Qdrant 启动可能慢于 API，`api` 配置了失败后重启，直到依赖可用。

### Linux 服务器实测记录（2026-09-29）

使用 Docker Engine 29.4.3、Docker Compose v5.1.3 执行 `up --build -d` 成功。`api` 和 `mock` 容器状态为 `healthy`；Qdrant 运行中且 `/healthz` 返回成功。`/health?readiness=true` 返回 `ready: true`，`database`、`vector`、`mock`、`state` 均为 `up`。见[版本](evidence/compose-server/docker-version.txt)、[容器状态](evidence/compose-server/ps.txt)、[API readiness](evidence/compose-server/health.json)和[Qdrant 健康检查](evidence/compose-server/qdrant-health.txt)。

外部 HTTP 冒烟覆盖政策回答、SQL 查询、订单查询、跨用户拒绝、缺参澄清、工单预览/确认/重复确认、受保护 Trace 与指标端点，结果见[检查汇总](evidence/compose-server/summary.json)、[工单 Trace](evidence/compose-server/trace.json)、[参数化 SQL Trace](evidence/compose-server/sql-trace.json)及同目录中的 SSE 文件。HTTP Golden 评测 49 条中通过 46 条、失败 0 条、跳过 3 条，关键安全失败 0；业务库前后原始文件 SHA256 一致。Golden 绑定 SQLite 逻辑数据 SHA256，可跨 Windows/Linux 核对相同业务数据；原始文件 SHA256 前后对比用于验证只读。3 条跳过项为故障注入场景，公开接口无法开启，进程内 49/49 评测已覆盖。见[服务器评测报告](evidence/compose-server/eval-report.md)。这些结果证明单次演示部署和功能冒烟，不代表负载能力或生产可用性。

目标机器上应检查：

```sh
curl -f http://127.0.0.1:8000/health?readiness=true
curl -f http://127.0.0.1:6333/healthz
curl -N -X POST http://127.0.0.1:8000/chat \
  -H 'Authorization: Bearer demo-user-a' \
  -H 'Content-Type: application/json' \
  -d '{"conversation_id":"deploy_smoke_001","message":"退货政策是什么？"}'
```

Windows PowerShell 使用 `curl.exe` 并把带反斜杠的请求合并为一行；README 给出可直接复制的示例。第一个检查应返回 `ready: true`，最后一条应至少收到 `message.delta` 和 `done` 事件。再以 `O00001` 检查订单工具，以 `demo-user-b` 查询 `O00001` 检查越权拒绝。执行 `docker compose -f docker/docker-compose.yml logs --tail=100 mock` 查看 mock 异常，但不要把令牌或完整原始数据记录到交付截图中。

服务就绪后可从仓库根目录运行完整合成数据冒烟脚本：

```sh
bash scripts/verify_compose.sh
```

脚本验证健康、指标、政策、SQL、订单授权、澄清、工单确认与幂等、Trace，并写入 `docs/evidence/compose-server/`。每次运行会创建一张 mock 工单并覆盖该目录中的对应证据文件；在需要保留历史记录时先复制证据目录。

## 数据与持久化

| 位置 | 用途 | 生命周期 |
| --- | --- | --- |
| 镜像 `/app/database/ecommerce.db` | 合成业务快照，连接以只读 URI 打开 | 随镜像重建 |
| `qdrant_data` | 政策向量索引 | Compose 数据卷 |
| `agent_state_data` | Trace、确认动作、幂等结果、Outbox | Compose 数据卷 |
| `mock_ticket_data` | Mock 工单 | Compose 数据卷 |

生成器与 `data_manifest.json` 记录 seed、文件哈希、数量和演示订单。修改知识文档、Schema、生成器或 seed 后，重新构建镜像并运行 `scripts/verify_data_manifest.py`。当前 API 启动时重建 Qdrant 集合；数据量仅约 30 篇文档，适合 MVP 演示。不要将真实用户数据混入合成资产。

停止服务：

```sh
docker compose -f docker/docker-compose.yml down
```

该命令保留数据卷；需要重置演示状态时，先备份或确认不再需要 Trace、工单与 Qdrant 索引，再按 Docker 数据卷管理流程处理。

## 环境变量

Compose 默认使用演示配置。可复制 `.env.example` 为本地 `.env` 并覆盖变量；不要把 `.env` 提交到仓库。

| 变量 | 作用 |
| --- | --- |
| `MOCK_RANDOM_SEED` | 固定合成数据版本，默认 `20260923` |
| `DATA_REFERENCE_TIME` | 可覆盖开发/测试环境相对月份的分析基准；使用带时区的 ISO 8601 时间 |
| `MOCK_INTERNAL_KEY` | API/Mock 共享内部服务密钥 |
| `METRICS_TOKEN` | `/metrics` 的运维令牌 |
| `MOCK_SCENARIO_CONTROL_ENABLED` | 只在开发/测试环境允许故障注入 |
| `LLM_PROVIDER` | `rules` 或 `openai_compatible` |
| `LLM_BASE_URL` / `LLM_MODEL` / `LLM_API_KEY` | 兼容模型端点配置 |

当前代码会在 `APP_ENV=production` 时明确拒绝启动，因为真实认证适配器尚未配置；即使设置了非默认 `MOCK_INTERNAL_KEY`、`METRICS_TOKEN` 与 `STATE_ENCRYPTION_KEY` 也不会解除这一限制。接入真实认证后，还需配置密钥服务、TLS、网络边界、状态库备份和留存策略，并重新做安全与容量验收。Compose 将 API 和 Qdrant 仅绑定到本机 `127.0.0.1`，mock 只在 Compose 内部网络访问。

演示环境中的“上个月”“本月”以 `data_manifest.json.generated_at` 为固定基准；`DATA_REFERENCE_TIME` 可覆盖，适用于跨月重放。Mock 的 `observed_at` 记录实际查询时间，不改变订单或物流的合成 `updated_at`。

## 日志、Trace 与故障定位

- `GET /health?readiness=true` 区分数据库、向量库、mock 和运行时状态库状态。
- `GET /metrics` 需 `X-Metrics-Token`，输出 Prometheus 指标；标签不包含用户或订单号。
- `GET /internal/traces/{trace_id}` 需 `demo-admin`，用于查看脱敏后的完整调用链。
- Mock 故障场景见 [mock 服务说明](../mock/README.md)。`rate_limit` 返回 429 和 `Retry-After`，`timeout` 延迟响应，`server_error` 返回 500。
- 若 API 启动反复失败，先看 Qdrant 与 mock 状态，再运行数据清单校验；若返回 503，读取健康检查中处于 `down` 的组件。

## 本地无容器运行

本地开发可使用内存 Qdrant：

```sh
uv sync --frozen --extra dev
uv run python scripts/generate_seed_data.py
uv run python scripts/verify_data_manifest.py
uv run uvicorn mock.mock_server:app --host 127.0.0.1 --port 8081 --no-access-log
```

另开终端运行 `uv run uvicorn api.main:app --host 127.0.0.1 --port 8000 --no-access-log`。运行前可将 `.env.example` 复制为 `.env`。启动后的验证请求与 Compose 相同。
