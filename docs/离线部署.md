# Linux x86_64 离线演示包

本流程面向已验证的 Linux x86_64 演示服务器，运行默认 `rules` 网关和固定种子合成数据。它不包含本地大模型权重；当前约 1.7 GiB 内存的服务器不适合运行文档示例中的 8B 模型。真实模型端点尚未提供，兼容接口的自动化测试仅验证协议、配置切换和结构化响应契约。

## 在线构建机制作

构建机需要 Linux x86_64、Docker Engine、Compose 插件、网络和足够磁盘空间。它会构建 Agent 镜像、获取固定版本 Qdrant 镜像、下载 `uv.lock` 中运行依赖的 Linux wheel，并生成 SHA256 清单。从仓库根目录运行：

```sh
python3 scripts/build_offline_bundle.py
```

如构建机需要使用指定 Python 包索引，可加 `--pip-index-url https://<索引地址>/simple`。已经确认本机 `aftersales-data-agent:local` 镜像由当前源码构建时，可加 `--reuse-images` 跳过重复镜像构建；该选项不会核对镜像与源码是否一致。

脚本输出 `runtime/offline-linux-amd64-<UTC时间>/`，其中包含：

| 文件 | 用途 |
| --- | --- |
| `images.tar` | Agent 与 Qdrant 的 Linux amd64 镜像归档 |
| `source.tar.gz` | 源码、离线 Compose、数据生成脚本和文档 |
| `requirements.txt`、`wheelhouse/` | 锁定运行依赖的 wheel，供将来重建使用；安装预构建镜像时不需要 pip |
| `model-manifest.json` | 声明本包使用规则网关、无模型权重文件 |
| `bundle-manifest.json`、`SHA256SUMS` | 平台、镜像 ID 和文件完整性校验 |
| `install.sh` | 离线安装和健康检查入口 |

把整个目录通过内网、移动介质或其他受控方式复制到目标服务器。目录中的镜像和 wheel 按 Linux amd64、Python 3.12 制作；其他系统架构需要重新构建。

2026-10-08 在当前 Linux x86_64 服务器生成了 `runtime/offline-linux-amd64-20261008T035244Z/`，约 242 MiB，包含 61 个 wheel。对应归档 `runtime/offline-linux-amd64-20261008T035244Z.tar` 的 SHA256 为 `33f7b9271a85806f9d2a0990831d8bea7debe5589fee1f4f2f1a88bd8b7bec87`；复制归档后可先核对该值，解包后安装程序还会检查目录内的全部文件。包内[清单](evidence/offline-compose/bundle-manifest.json)、[文件 SHA256](evidence/offline-compose/SHA256SUMS)和[运行环境](evidence/offline-compose/offline-run-info.txt)已保存为交付证据。

## 目标服务器安装

目标服务器只需已有 Docker Engine、Compose 插件及 `bash`、`tar`、`sha256sum`、`curl`；无需连接镜像仓库、PyPI 或模型服务。若复制的是上述 `.tar` 归档，先在归档所在目录校验并解包：

```sh
printf '%s  %s\n' '33f7b9271a85806f9d2a0990831d8bea7debe5589fee1f4f2f1a88bd8b7bec87' 'offline-linux-amd64-20261008T035244Z.tar' | sha256sum -c -
mkdir -p offline-mvp
tar -xf offline-linux-amd64-20261008T035244Z.tar -C offline-mvp
cd offline-mvp
```

随后在离线包目录运行：

```sh
bash install.sh
```

安装脚本先校验全部文件 SHA256，再载入镜像并解压源码。`scripts/init_qdrant_offline.sh` 创建 Qdrant 数据卷并等待健康端点；随后用 `docker/docker-compose.offline.yml` 启动 API 和 mock，禁止镜像拉取或构建。默认规则网关不调用外部模型服务；API 首次启动会从知识文档初始化 Qdrant 集合。API 和 Qdrant 端口只绑定目标机器的 `127.0.0.1`。

如需与现有演示栈并行验证，可在运行安装脚本时设置 `COMPOSE_PROJECT_NAME`、`API_BIND_PORT` 和 `QDRANT_BIND_PORT`，例如 `COMPOSE_PROJECT_NAME=aftersales-offline-check API_BIND_PORT=18000 QDRANT_BIND_PORT=16333 bash install.sh`。此时新栈使用独立数据卷和本机端口，不会替换原有容器。

安装后可手动复验：

```sh
cd project
docker compose -f docker/docker-compose.offline.yml ps
COMPOSE_FILE=docker/docker-compose.offline.yml bash scripts/verify_compose.sh
```

复验脚本会创建一张合成 mock 工单，并覆盖 `docs/evidence/compose-server/` 中相应的演示证据。三个 Compose 数据卷保存 Qdrant 索引、Agent 状态和 mock 工单；`docker compose ... down` 不会删除数据卷。
并行验证时，运行复验脚本也要传入与安装时相同的 `COMPOSE_PROJECT_NAME`、`API_BIND_PORT` 和 `QDRANT_BIND_PORT`。

这次安装发生在仍联网的同一台服务器，尚未验证物理断网或另一台干净主机，因此证据只证明安装过程没有请求构建或拉取镜像。默认规则网关不访问公网模型；如改为本地模型，需要另行提供硬件、模型文件与 SHA256、推理服务，并重新执行路由、SQL、工具与安全评测。
